# USDC → USDT 切り替え提案の評価と、代わりに着手すべきこと

作成日: 2026-08-04
対象読者: 共同パートナー / プロジェクト関係者
判断: **USDT への切り替えは行わない。** 別の 7 件が実損を出しており、そちらが優先。

---

## 1. サマリー

「USDC だと AI 判定が全然出ない。USDT にしたらどうか」という提案を受け、本番データ・
オンチェーン実測・コードの三方向から調査した。

結論は 3 つ。

1. **「判定が出ない」の原因は資産の種類ではない。** Base の Aave における USDC の
   稼働率が 2026-07-23 に 85% を超えた瞬間、AI の採点式が構造的に方向性判定
   （BUY/SELL）を出せなくなった。閾値まで **わずか 2 ポイント** 足りない状態が
   13 日間続いている。
2. **必要な提案は、実は 25 日間ずっと正しく出ていた。** 安全利回りの運用提案が
   3 日サイクルで 16 件生成されていた。問題は **一度も実行されなかった** こと。
3. **USDT に切り替えると、唯一正常稼働していたこの提案生成まで停止する。**
   Base の Aave にも Pendle にも USDT 市場が存在しないため。

調査の過程で、実損に直結するブロッカーが **7 件** 見つかった。USDT 化はその
いずれも解決しない。本書は 7 件を 3 つの構造に整理し、要件と優先順位を示す。

---

## 2. 調査で判明した事実

すべて本番 DB・Base メインネット RPC・本番コンテナの実測値に基づく。推測は含まない。

### 2-1. AI 判定の実績（直近 30 日）

```
prompt_version | action | count | avg_confidence
v4             | HOLD   |   178 |           41.8
v4             | BUY    |     4 |           69.8
```

- HOLD 率 **97.8%**
- 平均確信度 41.8 は、ルールエンジンが LLM 出力を強制的に HOLD へ潰すときの
  クランプ値（上限 45）と一致する。つまり 178 件は「AI が熟慮した末の様子見」
  ではなく、**機械的に打ち消された結果**
- BUY 4 件の日付: **7/11, 7/15, 7/21, 7/21 — すべて 7/22 以前**

### 2-2. Base / Aave における USDC の実測値

Base メインネット RPC から直接取得（本日時点）。

```
supply APY   :  3.36%
borrow APY   :  4.32%
供給総額     :  $176,224,283
変動借入残高 :  $152,283,770
稼働率       :  86.41%     ← これが引き金
```

金利モデルを上記実測値で校正し（`supply = borrow × util × (1 − 準備率)`、
準備率 10% で実測と完全一致）、APY 履歴から過去 31 日の稼働率を復元した。

| 期間 | 稼働率 | AI の判定可否 |
|---|---|---|
| 7/05 – 7/22 | 77.5 – 83.6% | 条件次第で BUY 成立（実際に 4 件発生） |
| **7/23 – 8/04** | **86.9 – 88.8%** | **13 日間すべて不成立** |

採点式は稼働率 85% 超で大きく減点する設計になっており、その結果スコアが
確信度 68 に留まる。採用に必要な閾値は 70。**2 ポイント差で 13 日間落ち続けている。**

### 2-3. 提案の生成と、その後

```
id  user  operation  asset  amount   status    created     expires
17   16   SUPPLY     USDC   $1,000   canceled  2026-07-10  2026-07-13
18   16   SUPPLY     USDC   $1,000   canceled  2026-07-13  2026-07-16
...（3 日おきに 14 件が同じ経過をたどる）...
31   16   SUPPLY     USDC   $1,000   pending   2026-08-03  2026-08-06
32   11   SUPPLY     USDC     $460   pending   2026-08-04  2026-08-07
```

- **提案パイプラインは 25 日間、寸分の狂いなく正常稼働していた**
- `canceled` は **ユーザーによる拒否ではなく、72 時間の期限切れ**
- **承認・実行は 0 件**
- 金額が 25 日間一定（$1,000 / $460）＝ **残高が一度も動いていない**＝一度も実行されていない
- 提案額は残高の 10% で算出されるため、推定で **約 $14,600 が 25 日間ゼロ利回りで滞留**

手数料は取引の実行に対して発生する。**実行ゼロは収益ゼロを意味する。**

### 2-4. なぜ実行されなかったか

ユーザーごとに原因が異なっていた。

**山本さん（user 11 / 完全おまかせモード）**

```
delegation_grants where user_id = 11  →  0 行
```

承認不要の「完全おまかせ」設定でありながら、実行に必要な委譲枠が
**一度も存在しなかった**。バックエンドは委譲枠が無い提案を黙って承認待ちに戻す
設計のため、おまかせのはずのユーザーが承認画面を見に行かないまま 72 時間で
期限切れになる、という循環が 7 回繰り返された。

根本原因はフロントエンドのビルド時フラグ `NEXT_PUBLIC_DELEGATION_CONSENT_ENABLED`
が **本番で無効（既定値）** だったこと。この状態で「完全おまかせ」を選ぶと、
委譲同意フローが丸ごとスキップされ、**運用モードの表示だけが変わって実行権限は
発行されない**。

つまり **「ユーザーへの表示」と「実行できる状態」が独立に更新でき、乖離しても
誰も気づかない** 構造だった。

**テストパートナー（user 16 / 承認要求モード）**

提案を承認するには通知が要る。しかし本番の通知経路は **両方とも無効** だった。

| 経路 | 状態 |
|---|---|
| LINE | `LIFF_ID` が未設定 → LINE 認証自体が機能しない |
| Web Push | VAPID 鍵が未設定 + 購読 UI が画面に未配置 + 購読情報がメモリ保持 |
| Slack（運用者向け） | 稼働中（30 日で 1,223 件） |

エンドユーザーに届く経路が **1 本も存在しない**。提案の存在を知る手段が無い状態で
「承認されない」のは当然だった。

なお本番ユーザーは全員 Privy 経由（メール / ソーシャルログイン）で登録されており、
LINE ID を持たない。Privy 側の設定は完備している。

### 2-5. 25 日間、誰も気づかなかった理由

コードベース全体が **fail-open**（失敗しても処理を止めない）で統一されている。
設計としては正しいが、委譲枠の欠如も通知の失敗も警告ログに残るだけで、
Slack 通知にもダッシュボードにも現れない。

**個々の不具合より、この可観測性の欠如そのものが重い。**

## 3. USDT では解決しない理由

### 3-1. 技術的に不可能

Aave V3 の Base デプロイに **USDT リザーブは存在しない**。全チェーンを横断確認した
結果、USDT は Ethereum / Plasma / Monad / Mantle / Polygon / BSC / Avalanche には
あるが、**Base には無い**。

対象資産を USDT に変更すると、トークンアドレスの解決に失敗して市場データが
すべて空になり、AI の入力が消える。判定は改善するどころか **確定的に停止する**。
供給の実行自体も失敗する。

Pendle も同様で、Base で稼働中の市場は 5 本、**すべて USD / USDC 建て**。
現在ルーティング先としている市場も含め、USDT 版は存在しない。

### 3-2. 流動性

Base 上のステーブルコイン供給は **約 90% が USDC**。USDT に替えると入出金のたびに
スワップが挟まり、薄い流動性でスリッページを払うことになる。全ユーザーのコストに
直結する。

### 3-3. 規制

- **EU**: MiCA の移行期間終了に伴い、2026 年 7 月 1 日付でライセンス取得済み
  取引所は USDT を上場廃止。Tether は準備金要件を理由に認可を申請していない
- **日本**: 改正資金決済法の下で海外発行ステーブルコインの流通経路が開いたが、
  国内で実際に流通しているのは USDC

本プロダクトは日本の個人向けであり、税務連携も組み込んでいる。USDT の採用は
**規制適合性を自ら下げる方向の意思決定**になる。

### 3-4. 提案に含まれていた正しい直感

一点だけ拾うべき核がある。「今の運用先は利回りが出ていない」という感覚は正しい。

| 運用先 | 資産 | 規模 | 利回り |
|---|---|---|---|
| Morpho（Steakhouse） | USDC | $580M | 4.31% |
| Morpho（Gauntlet） | USDC | $429M | 4.31% |
| Fluid | USDC | $9.2M | 5.40% |
| **Aave（現行）** | **USDC** | **$22M** | **3.36%** |

ただしこれは **資産ではなく運用先の問題**。同じ USDC・同じ Base のまま、
規模で 26 倍・利回りで約 +1 ポイント改善できる選択肢が実在する。
しかも該当プロトコルのクライアント実装は既にリポジトリに存在する。

**USDT 化より圧倒的に費用対効果が高く、規制上の後退も伴わない。**

## 4. 代わりに着手すべきこと

7 件のブロッカーを独立の不具合として並べると、同じ形で再発する。共通構造は 3 つ。

| クラスタ | 含むブロッカー | 一言で |
|---|---|---|
| **A. 約束と実行能力の乖離** | 委譲未発行 / サイレント失敗 / 72h 期限 | ユーザーに見せている状態を、システムが実行できない。しかも誰にも見えない |
| **B. 到達経路の不在** | LINE 無効 / Web Push 無効 | 提案型プロダクトなのに、提案が誰にも届かない |
| **C. 判定モデルと商品価値の不一致** | 稼働率 85% / リスクモード制約 | ドル建ての利回り運用を、相場の方向性判定でゲートしている |

---

### クラスタ A — 約束と実行能力の乖離

**本質的な課題**

ユーザーに提示した運用状態と、システムが実際に実行できる状態が、独立して変更でき、
乖離しても検知されない。これは機能の不足ではなく **状態設計の欠陥** であり、
フラグ 1 つで再発する。

**ユーザーが本当に得たい価値**

「おまかせ」を選んだ人が欲しいのは、判定でも提案でもなく **預けた資金が実際に
運用されていること**。そしてより深いところでは **「表示されている状態を信じてよい」
という信頼**。金融プロダクトで表示と実態が食い違い、本人にも運営にも見えないのは、
機能不全より重い。

**スコープ**

やること
- 「完全おまかせ」と「有効な実行権限を持つ」が同値である、という不変条件をシステムに表明させる
- 不変条件が破れた状態を検知し、(a) 運営に通知 (b) 安全側に縮退 (c) ユーザーに縮退を伝える
- 「実行されるはずが実行されなかった」事象を握り潰さず必ず可視化する

やらないこと
- 委譲同意フロー自体の再設計（実装は存在し、フラグで無効化されているだけ）
- 縮退からの自動復旧（ユーザーの再同意が要る領域にシステムが踏み込まない）
- 過去 14 件の期限切れ提案の遡及的な再生成

**成功の定義**
- 「おまかせ」表示のユーザーが、例外なく有効な実行権限を持っている
- 不変条件違反の発生から運営が知るまで **1 時間以内**（現状: 25 日間ゼロ）
- 「実行されるはずが実行されなかった」件数が 0 とダッシュボードで確認できる

**主なリスク**
- **安全側への自動縮退は、ユーザーには「勝手にモードが変わった」と映る。**
  通知できなければ縮退は新たな不信を生むだけ。**A の縮退機能は B に依存する**
- 可観測性を伴わない fail-open は「静かな故障」を量産する。ここを直さずに機能を
  足すと、同じ 25 日が別の場所で繰り返される

---

### クラスタ B — 到達経路の不在

> **決定: Web Push（PWA）を主軸に据える。消費者ローンチが近いため必須要件。**

**本質的な課題**

「AI が提案し、ユーザーが承認する」という商品の中核ループが、通知手段を
**一度も持ったことがない**。

構造的に重要なのは、届かない提案が「生成された」として記録され続けたこと。
承認率という指標が、実際には **見られてすらいない母数** の上で計算されていた。

**ユーザーが本当に得たい価値**

- 承認型: **自分の判断が必要なときに呼ばれること**。毎日アプリを開く義務を負わないこと
- おまかせ型: **通知は本来不要**。ただし事後報告は要る

この非対称性が設計上重要。**おまかせ型は通知が無くても価値を提供できるが、
承認型はできない。**

**スコープ**

やること
- 承認を要する提案について、到達可能な経路を最低 1 本確立する（Web Push）
- **到達可能な経路が 1 本も無いときは、承認型の提案を作らない**。届かない提案を
  作って期限切れさせるのは、体験の毀損に加えて **指標を汚染する**
- 「送信した」と「到達した」を区別して記録する。現在の通知記録は宛先種別しか
  持たず、配信結果を持たない

やらないこと
- 全チャネルの網羅（メール送信は実装がゼロ。今は不要）
- リッチな通知体験の作り込み
- LINE MINI App の再申請を前提とした設計

**成功の定義**
- 承認型ユーザーへの提案について **到達率が測定可能**（現在は測定手段すら無い）
- 提案から初回接触までの中央値が、期限に対して十分短い
- 「送ったが届かなかった」件数がデータで言える

**主なリスク（最重要）**
- **iOS の Web Push は、ホーム画面に追加された PWA でのみ動作する。**
  日本の個人向けプロダクトで iPhone 比率が高い場合、「ホーム画面に追加してもらう」
  という一段のハードルが到達率の上限を決める。**消費者ローンチの前提として、
  この導線設計を先に固める必要がある。** 技術課題ではなくオンボーディング設計の課題
- チャネルを増やすほど到達判定が難しくなる。**増やす前に 1 本で到達を測れる状態を作る**
- 通知記録が「意図」を残して「結果」を残していない現状のままでは、到達率を語ると
  また誤読が起きる（本調査でも、DB に残る 16 件の記録を配信実績と誤読しかけた）

---

### クラスタ C — 判定モデルと商品価値の不一致

> **決定: 安全利回りを土台に、方向性判定を上乗せする 2 フェーズ構成。**

**本質的な課題**

ドル建てステーブルコインを貸して金利を得る行為を、暗号資産相場の方向性判定で
ゲートしている。安全利回りへの配分に、相場の強気確信は必要ない。

この不一致は既にコード内で認識され、「様子見判定でも安全利回りの提案は出す」
という形で回避策が入り、有効化され、**25 日間正しく機能していた**。
つまり **土台部分は既に動いている**。

**ユーザーが本当に得たい価値**

「AI 判定が出ない」を問題として立てた時点で、暗黙に「相場を読む AI」を前提に
している。しかし 25 日間のデータが示したのは、**安全な運用に必要な提案は出ていたが
実行されなかった** という事実だった。

**判定数はユーザー価値ではない。運用されている資産額が価値である。**
USDT 提案も「判定数」という代理指標を追ったものだった。

**スコープ**

フェーズ 1（土台 / 先行）
- 安全利回り経路を主経路として位置づける
- 運用先の選択肢を広げる（同一資産・同一チェーンで、より深く高い利回りの選択肢が実在）
- 運用先の選択を固定値ではなく実勢利回りに基づかせる

フェーズ 2（上乗せ / 後続）
- 方向性判定の採点式を、供給専業の商品性に合わせて補正する
- 「強気と判定する閾値」と「その判定を採用する閾値」が噛み合っていない死角を解消する

やらないこと
- **USDC → USDT の変更**
- チェーン移行
- リスクモードの引き上げを、A と B の解決前に行うこと
- 「判定を増やすこと」自体を目的とした調整

**成功の定義**
- **遊休資金比率**（預かり資産のうちどのプロトコルにも入っていない割合）を
  北極星指標として定義し、継続的に低下させる
- 判定数・提案数を **指標から降格** する（活動量であって成果ではない）

**主なリスク**
- 判定を出やすくする調整を A・B 未解決のまま行うと、**期限切れ提案が増えるだけ**。
  「改善したのに数字が悪化する」状態を作る
- リスクモードを上げる判断はリスク開示と同意の設計を伴う。技術的には軽微だが
  **責任の所在が変わる**
- 外部プロトコルの利回りは変動する。「今この運用先が良い」を固定値で持つと、
  稼働率 85% と同じ固定閾値問題を再生産する

## 5. 横断的な成功の定義

個別の修正が終わったかではなく、次の状態に到達したかで判断する。

| 観点 | 現状 | 目標状態 |
|---|---|---|
| 資金 | 遊休 ≒ 100% | 遊休比率が継続的に低下 |
| 約束の一貫性 | 表示と実態が乖離、検知なし | 乖離が発生し得ない、または即時検知 |
| 到達 | 測定手段すら無い | 到達率が測定でき、期限内に接触 |
| 可観測性 | 25 日間気づけない | 異常を 1 時間以内に検知 |
| 中核指標 | 判定数（代理指標） | 運用資産額（成果指標） |

## 6. 優先順位

消費者ローンチが近いため、B を必須要件として扱う。

```
① 可観測性（A の一部）
   └ 最も安く、最も効く。これが無いと「直ったか」が判定できない

② 実行権限の回復（A）
   └ おまかせユーザーの運用が今日から成立する。通知に依存しない

③ 到達経路 1 本（B / Web Push）
   └ 消費者ローンチの必須要件。iOS のホーム画面追加の導線設計を含む

④ 不変条件と安全縮退（A）
   └ ③ が前提。通知できない状態で縮退させると不信を生む

⑤ 運用先の拡張（C フェーズ 1）
   └ 同一資産・同一チェーンで利回り改善

⑥ 方向性判定の補正（C フェーズ 2）
   └ 「判定を増やす」修正。①〜④ の前に入れると期限切れの母数が増えるだけ
```

**可観測性を最初に置く理由**: 25 日間気づけなかったのは個別のバグではなく、
可観測性の欠如そのもの。これを直さずに他を直すと、直ったかどうかが分からない。

**方向性判定を最後に置く理由**: これは「判定を増やす」修正。届ける経路と
実行する権限が整う前に入れると、期限切れの母数を増やすだけになる。

## 7. 共同パートナーへの回答（要約）

> 提案は 25 日間、3 日おきに正確に生成され続けていました。止まっていたのは
> 「おまかせモードなのに実行権限が発行されていなかった」ことと
> 「通知経路が両方とも未設定だった」ことで、USDC か USDT かは関係ありません。

> 運用先の問題として、同じ USDC・同じチェーンのまま対応します。

## 付録: 検証手順

本書の主張はすべて再現可能。

```bash
# 判定実績
docker exec <postgres> psql -U ultra -d ultra_autotrade -c "
SELECT prompt_version, action, COUNT(*), ROUND(AVG(confidence),1)
FROM ai_decisions WHERE created_at > NOW() - INTERVAL '30 days' GROUP BY 1,2;"

# 提案の経過
docker exec <postgres> psql -U ultra -d ultra_autotrade -c "
SELECT id,user_id,operation,asset,amount,status,created_at::date,expires_at::date
FROM proposals WHERE created_at > NOW() - INTERVAL '30 days' ORDER BY id;"

# 委譲枠の有無
docker exec <postgres> psql -U ultra -d ultra_autotrade -c "
SELECT id,user_id,status,expires_at,
       (status='active' AND revoked_at IS NULL AND expires_at > NOW()) AS is_valid
FROM delegation_grants;"

# 通知・委譲・LINE 設定の実効値
docker exec <backend> env | grep -E '^LINE_|LIFF|VAPID|DELEGATION'

# Web Push 配信経路の生存確認（0 なら未登録）
docker logs <backend> 2>&1 | grep -c 'LINENotificationSender: 設定済み'
```

Base 上の稼働率と利回りは、パブリック RPC への `getReserveData` 呼び出しと
`aToken` / 変動債務トークンの総供給量から誰でも再計算できる。
過去の稼働率は公開 API の利回り履歴から金利モデルを逆算して復元した。
