# 第 I 部 — 制約

## I-1. 既存コードへの統合方針

> **原則: 新規ファイル・新規テーブル・新規抽象を作らない。**
> 本件はすべて「既に存在するが、無効化されている / 配線されていない / 見えていない」
> ものの復旧である。新規実装として扱うと、既存の重複を生む。

### クラスタ A（約束と実行能力の乖離）— 新規ファイル 0 / `main.py` 変更 0

| やること | 統合先 | 理由 |
|---|---|---|
| 不変条件の検査 | `automation/ai_judgment_scheduler.py` の `_create_proposals_for_users` / `_create_safe_yield_proposals_for_users` | 両者とも既に「有効かつ執行ポリシー該当」のユーザーをループしている。検査 1 クエリを足すだけで済み、新規ループも起動時配線も不要 |
| 委譲枠欠如の可視化 | `proposals/auto_execute.py` の grant 無し分岐 | **既に検知はしている**。黙って承認待ちに戻している箇所に通知を足すだけ |

> #### 2026-08-05 改訂: 「新規テーブルを作らない」を購読情報について上書きした
>
> 上表の「購読情報の永続化 = `notification_settings_json` に同居 / 新規テーブルを作らない」は、
> 実装後に **lost update** を生むことが判明したため撤回する。
>
> **理由**: 同一セルに購読配列と通知設定（`push_enabled` / `preferences`）が同居し、
> 書き手が2系統（`DatabaseSubscriptionStore` = 独自セッション、`PUT /settings` = リクエスト
> セッション）あり、双方が read-modify-write する。並行実行で購読1件または設定変更1回が
> **黙って消える**（スケジューラの410パージとユーザーの設定保存が同時、2端末同時購読など）。
>
> 代替案として行ロック（`with_for_update`）と楽観的CASを検討したが、
> 前者は SQLite で無効化されテスト不能かつ `add()`/`remove()` の全ユーザー走査と併せて
> 全行ロックになる。後者は `Session.rollback()` が呼び出し元の SAVEPOINT を破棄する等の
> 副作用があり付帯物が増える。**専用テーブルなら read-modify-write 自体が無くなり、
> endpoint のグローバル一意性も DB 制約が保証する**（旧実装は全ユーザー走査で模倣していた）。
> 結果としてコード量も減る。
>
> **本番データの移行コストが無いことを確認済み**: 本書の到達経路表のとおり本番は
> VAPID 鍵未設定で、永続化された購読は 0 件。マイグレーションには staging/dev 向けに
> backfill を実装している。
>
> 元規定の趣旨は「既存機能の重複実装を避ける / スコープ膨張を防ぐ」であり、
> 並行制御の正しさは別軸のため、この一点に限って上書きする。
> 購読 API・送信クラス・購読 UI についての「新設しない」方針は**引き続き有効**。
>
> 実装: Alembic `z7a8b9c0d1e2` / `backend/app/notifications/models.py::PushSubscription`

## I-2. 守るべき設計原則・既存パターン

### 金融計算
- **金額計算は `Decimal` のみ。`float` 禁止**（CLAUDE.md セキュリティルール 11）
- API レスポンスの `Decimal` は**文字列**で返す。フロントは `Number()` でラップしてから整形する
- 非 18 桁トークンの桁数を推測しない（USDC = 6）

### 失敗の扱い
- **`fail-open` は維持する。** 外部 I/O の失敗で判定ジョブ全体を落とさない設計は正しい
- **ただし可観測性とセットにする。** 握り潰すなら必ず「ログ + 通知」を伴わせる。
  今回の 25 日間の空回りは、fail-open それ自体ではなく **可観測性を伴わない fail-open** が原因
- **per-user SAVEPOINT**（`db.begin_nested()`）を維持する。1 ユーザーの DB エラーが
  セッションを汚染して後続ユーザー全員を巻き込む問題への既存対策。素朴な全体ロールバックは不可

### 設定フラグ
- 新規フラグは **既定 OFF・明示 opt-in**。命名は既存に倣い `<DOMAIN>_<FEATURE>_ENABLED`
- **`NEXT_PUBLIC_*` は build-time 埋め込み。** 値を変えたら frontend の再ビルドが必須。
  環境変数を足しただけでは反映されない（今回の根本原因そのもの）
- 異常時に「env を戻すだけで即無効化できる」kill switch 性を保つ（再デプロイ不要）

### API / 認可
- 新規エンドポイントには RBAC を必ず実装する
- 認証状態で表示が変わる操作系 UI は、未ログイン時にガードする

### 消費者向け表現
- **消費者向け UI にプロトコル名（Aave / Pendle / Lido 等）を出さない。**
  既存コミットで徹底されている方針。安全利回り提案の理由文もこれに従っている
- 全テキストは日本語。翻訳キーがあればそれを使う。英語ハードコード禁止
- ダミー値・ハードコードされた数値を UI に置かない。未取得時は「データなし」を表示

### ファイル・コミット
- 1 ファイル 500 行上限 / 1 コミット 5 ファイル上限
- `package.json` を変更したら `package-lock.json` も同時にコミット

## I-3. やってはいけないこと

### 設計・スコープ
1. **USDC → USDT への変更**。Base の Aave にも Pendle にも USDT 市場が無く、
   唯一正常稼働している提案生成を停止させる
2. **チェーン移行**を本要件に混ぜる
3. **`_DIRECTIONAL_THRESHOLD`（採用閾値）や確信度の算出式を直接触る。**
   これらは売り判定側にも波及し、過去に発生した売りシグナル連発の再燃リスクがある。
   稼働率バンドの補正は買い側に有利・売り側に不利な非対称変化のため安全だが、
   閾値そのものを下げると対称に効いてしまう
4. **安全装置の配線変更**（HF チェック / 緊急停止フラグ / クールダウン / 取引上限）を
   本要件に含めない。これらは Tier S の直列作業
5. **リスクモードの引き上げ**（Pendle 開放）をクラスタ A・B の完了前に行わない
6. **新規の集約層・抽象の追加**。既存の Adapter 注入方式で足りる

### 順序
7. **縮退機能（安全側への自動降格）を、到達経路より先に入れない。**
   通知できない状態で勝手にモードを変えると、ユーザーには「無断で設定が変わった」
   としか映らず、不信を増やすだけになる
8. **判定を出やすくする修正を、実行権限と到達経路の復旧より先に入れない。**
   期限切れ提案の母数が増えるだけで、指標は悪化する
9. **可観測性の整備を後回しにしない。** これが無いと「直ったか」が判定できない

### 運用
10. **`sed -i` でのファイル編集**（.env で前行連結バグを起こす）。`awk` + 一時ファイル + `mv`、
    環境変数の追記は `printf '\nKEY=VALUE\n'`
11. **production VPS 上での `git commit` / `git merge` / エディタ直接編集**。pull only
12. **手打ちの `docker compose build`**。デプロイスクリプト経由のみ
13. **Tier S ファイルの同日複数 PR**（`main.py` / `requirements.txt` / `package.json` /
    `database.py` / スケジューラ本体 / CI 設定）
14. **VPS のパス構造を推測しない。** dev のみ `main/` サブディレクトリがあり、
    staging / production には無い。SSH 直後に必ず確認する

### 品質
15. **届かない提案を作り続けること。** 到達経路が 1 本も無い状態で承認型の提案を
    生成するのは、体験の毀損に加えて承認率という指標を汚染する
16. **型チェック・lint・単体テストの通過だけを根拠に「完了」と書くこと**

## II-3. ユーザーがやりそうなイレギュラーな操作

> **本節が最も重要。** 今回の 25 日間の空回りは、まさにこの類の操作
> （フラグ無効下でのモード切替）で発生した。

| # | 操作 | 想定される破綻 | 期待する挙動 |
|---|---|---|---|
| **I-1** | 「おまかせ」→「自分で承認」→「おまかせ」を短時間で往復する | **既知の実障害。** 同一の署名者を再度追加しようとして重複エラーになり、同意が失敗する。既存コードにも本番実機で再現した記録が残っている | 有効な実行権限が既にあれば再同意を要求しない。方針が変わる場合のみ、既存を外してから作り直す |
| **I-2** | 委譲同意の途中でアプリ・ブラウザを閉じる | 署名者は追加されたが実行権限が未確定。**今回発生した乖離と同じ形** | 中断を検知し、署名者を巻き戻す。中途半端な状態でモード表示を変えない |
| **I-3** | iPhone と PC の 2 台で通知購読する | 片方にしか届かない / 二重に届く | 複数購読を保持し、全端末に配信する。重複は許容する |
| **I-4** | 通知を許可した後、OS 設定で後から拒否する | 購読は残るが配信は永久に失敗し続ける | 失効を検知して購読を除去し、**到達経路ゼロのユーザーとして扱う** |
| **I-5** | PWA をホーム画面から削除して再追加する | 配信先が変わり、古い購読が死んだまま残る | 新規購読を受け付け、古い購読は失効検知で除去する |
| **I-6** | 承認待ちの提案がある状態で運用モードを変更する | 提案の前提（実行方式・許可プロトコル）と実際の権限が食い違う | モード変更時に既存の承認待ち提案を失効させるか、新方針で再評価する。**放置しない** |
| **I-7** | 承認ボタンを連打・二重タップする | 同一提案が二重実行される | 冪等に扱う。二重実行を防ぐ |
| **I-8** | 期限切れの直前に承認する | 承認処理の最中に期限切れ処理が走る（競合） | どちらか一方の結果に確定させる。「承認したのに期限切れ」を発生させない |
| **I-9** | 全額出金した直後に提案が届き、それを承認する | 実行時に残高不足で失敗する | 実行直前に残高を再確認し、失敗を明示する。無言の失敗にしない |
| **I-10** | 実行権限の有効期限が、承認待ち提案の期限より先に切れる | 承認は通るが実行できない | 提案生成時に権限の残存期間を考慮する。または実行時に検知して通知する |
| **I-11** | 圏外・機内モードで承認し、復帰後にリトライされる | 二重実行 | I-7 と同じ冪等性で吸収する |
| **I-12** | 別々のブラウザ（Safari / Chrome）で同一アカウントにログインし、同じ提案を同時に承認する | 二重実行 | サーバ側で一意性を担保する。クライアント側の制御に依存しない |
| **I-13** | リスクモードを変更した直後に、変更前の前提で作られた承認待ち提案を承認する | 許可されていない運用先に資金が入る | 実行直前にリスクモード適合性を再検証する |
| **I-14** | **通知設定で提案通知を無効にしたまま、承認型モードを使い続ける** | 到達経路ゼロが自ら再現される。**今回と同じ構造** | 承認型 + 到達経路ゼロの組合せを検知し、ユーザーに警告するか、提案生成を止める |
| **I-15** | 長期間アプリを開かず、承認待ち提案が何度も期限切れになる | 今回発生した 14 回の空回り | 一定回数の連続期限切れを検知し、運営に通知する。**同じ提案を無限に作り直さない** |
| **I-16** | 入金前に「おまかせ」を選ぶ | 最低入金額を満たさず提案が作られない。ユーザーには理由が見えない | 入金が必要である旨を明示する。無言でスキップしない |
| **I-17** | 実行権限を付与した直後に、すぐ取り消す | 実行中の処理が権限失効に遭遇する | 実行中の処理を安全に中断するか、完了まで保護する。中途半端な状態を残さない |

**このうち I-1・I-2・I-14・I-15 は、今回の障害と同じ構造を持つ。回帰テストとして必須とする。**

## II-4. テストの実装規約

- 配置は `backend/tests/<モジュール名>/` のサブディレクトリ構成に従う（既存 360 ファイル）
- 新規機能には必ず単体テストを追加する
- **自分が書いた単体テストの通過だけを検証完了としない**
- UI 変更を伴う場合は E2E を追加する。既存 spec は `frontend/e2e/` 配下
- **E2E の URL はルートグループを含めない。** ディレクトリ名が URL に現れない仕様のため、
  ナビゲーションリンクの実値を確認してから記述する。過去に誤 URL が長期間見逃された事例がある
- ステータスコードの緩い判定（`< 500` 等）だけで通過させない。404 が素通りする

# 第 IV 部 — リスクと未確定事項

## IV-1. 最大のリスク: iOS における Web Push の到達率

**iOS の Web Push は、ホーム画面に追加された PWA でのみ動作する。**
日本の個人向けプロダクトで iPhone 比率が高い場合、「ホーム画面に追加してもらう」
という一段のハードルが、到達率の構造的な上限を決める。

これは技術課題ではなく **オンボーディング設計の課題**であり、消費者ローンチの
前提条件として先に固める必要がある。受け入れ条件 B-7 はこの点を明示的に問う。

**未確定**: ホーム画面追加を促す導線をどこに置くか（初回ログイン時 / 入金完了時 /
初回提案時）。到達率の目標値をいくつに置くか。

## IV-2. 縮退と通知の依存関係

クラスタ A の「安全側への自動降格」は、ユーザーには「無断で設定が変わった」と映る。
**通知できない状態で降格を実装すると、機能不全を不信に変換するだけ**になる。

したがって **B（到達経路）→ A（降格）の順序を厳守する**。逆順は禁止事項 7 に記載。

## IV-3. 可観測性を伴わない fail-open の残存

本件で扱う範囲以外にも、同じ構造の握り潰しがコードベース全体に存在する可能性が高い。
本要件では「本件で触る箇所」に限定するが、**同種の箇所を棚卸しする作業を別途起票すべき**。

## IV-4. 外部利回りの変動と固定閾値

稼働率 85% という固定閾値が今回の障害を生んだ。運用先の選択でも同じ過ちを繰り返さないよう、
「今この運用先が良い」を固定値で持たないこと（受け入れ条件 C1-1）。

## IV-5. 本要件に含めない、が近接している事項

- リスクモードの引き上げ（Pendle 開放）— リスク開示と同意の設計を伴い、責任の所在が変わる
- LINE 認証経路の復旧 — 本番で無効。消費者ローンチの主軸を Web Push とする判断により、
  本要件のスコープ外とする。ただし **将来復活させる場合、通知経路が 2 本になることで
  到達判定が複雑化する**点を設計時に織り込むこと
- メール通知 — 送信基盤の実装がゼロ。到達確実性の担保として将来の選択肢に残す
