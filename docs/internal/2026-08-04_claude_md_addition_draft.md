## プロダクト原則（2026-08-04 追加 — 実行パイプライン 25 日間停止の調査より）

### 0. 目的とスコープ

**Ultra AutoTrade は、預けられた USD 建て資産を、本人の判断負荷なしに、安全な利回りへ
配分し続けるプロダクトである。**

- 中核価値は **運用されている資産額**。AI 判定の回数・提案の件数は活動量であって成果ではない
- 相場の方向性判定（BUY / SELL）は**上乗せ**であり土台ではない。ドル建ての利回り配分に
  相場の確信は要らない
- スコープ外: 運用資産の変更（USDC 固定）／チェーン移行／裁量トレード

**この 3 点が施策の可否を判断する最上位の基準。**
「判定が出ない」「提案が少ない」を課題として立てる前に、
**運用されている資産額が増えるか**を問うこと。

> 背景: 「USDC だと判定が出ないので USDT にしては」という提案の調査で、
> 必要な提案は 25 日間ずっと出ていたが一度も実行されていなかったことが判明した。
> 追っていたのは代理指標だった。

### 1. 状態設計 — 「表示」と「実行能力」を分離しない

ユーザーに提示した状態（例:「完全おまかせ」）と、システムが実際に実行できる状態
（例: 委譲枠の有無）を、**独立して更新できる設計にしてはならない**。

- 両者を結ぶ**不変条件をコードに表明する**
- 破れたら **「検知 → 通知 → 安全側へ縮退」の 3 点セット**。1 つでも欠けたら実装したことにならない
- **縮退は必ずユーザーに伝える。** 無断の設定変更は、機能不全より重い不信を生む

### 2. fail-open は可視化とセット

fail-open（失敗しても処理を止めない）は維持する。**ただし握り潰すなら必ずログ＋通知。**

可視化を伴わない fail-open は「静かな故障」を量産する。
25 日間気づかれなかった実行停止の原因は、fail-open それ自体ではなく**可視化の欠如**だった。

- 新規に `except: pass` や warning ログのみを書かない
- **「本処理を止めない」と「誰にも知らせない」は別物**

### 3. フラグの縮退先が安全側であること

新規フラグは既定 OFF・明示 opt-in（既存ルール）。
**加えて、OFF のときの挙動が安全側であることを必ず設計する。**

> 悪い例（実際に発生）: 同意フローのフラグが OFF のとき、
> **同意をスキップして状態表示だけ変更した**。
> 正しい縮退は「そのモードを選べない」だった。

- 「フラグ OFF = 機能が無効」ではなく **「フラグ OFF = そこに至る導線ごと閉じる」**
- フラグを追加する PR では、**OFF 時の挙動をテストで固定する**

### 4. 通知 — 届かないものを作らない

**到達可能な経路が 1 本も無い状態で、ユーザーの操作を要する対象（承認待ち提案等）を作らない。**

- 体験の毀損に加え、承認率などの**指標を汚染する**
- **「送信した」と「到達した」を必ず区別して記録する。** 宛先種別の記録は配信実績ではない

### 5. 外部変動値に固定閾値を置かない

外部プロトコルの稼働率・利回り等に対する固定閾値は、市場が動いた瞬間に機能を停止させる。

> 実例: 稼働率 85% の固定閾値により、外部の値が 86% に動いた日から
> 方向性判定が 13 日間ゼロになった。閾値まで **2 ポイント**足りない状態が続いていた。

- 閾値を置くなら、**その閾値を跨いだことを検知・通知する**
- 「今この値が良い」を定数で持たない

### 6. 消費者向け表現

**消費者向け UI にプロトコル名（Aave / Pendle / Lido 等）を出さない。**
提案理由・エラー文言・メタ情報を含む。

### 7. 統合方針 — 新規を作る前に既存を探す

新規ファイル・テーブル・エンドポイント・抽象を作る前に、必ず既存を確認する。

- 障害の多くは「**無効化されている / 配線されていない / 見えていない**」だけで、実装は存在する
- **`main.py` を触らずに済む設計を優先する**（Tier S / 1 日 1 PR）。
  新規バックグラウンドループは起動時配線で必ず `main.py` を触るため、
  既存ループへの相乗りを先に検討する
- 永続化が要るとき、**既存の JSON カラムで足りないか**を先に検討する（新規テーブルの前に）

### 8. テストで最低限意識すること

- **境界値は「上 / ちょうど / 下」の 3 点**。閾値バグは境界でしか出ない
- **2 つの閾値が連動する箇所は、その間の帯を明示的にテストする**
  （例: 強気と判定する閾値 65 と、その判定を採用する閾値 70 の間の死角）
- **ユーザーのイレギュラー操作を必ず含める。**
  最低限: モードの往復 / フロー途中での離脱 / 複数端末 / 長期未操作 / 二重操作
- **過去の実障害は回帰テストとして残す**
- 自分が書いた単体テストの通過だけを検証完了としない（既存ルール）

### 9. 命名・エラーハンドリング

| 対象 | 方針 |
|---|---|
| 環境変数フラグ | `<DOMAIN>_<FEATURE>_ENABLED`。既定 OFF、明示 opt-in |
| DB 永続値・enum | リネーム禁止。値の真実源は `models.py`（既存ルール） |
| テスト配置 | `backend/tests/<モジュール名>/` のサブディレクトリ |
| 外部 I/O の失敗 | fail-open + ログ + 通知（§2） |
| ユーザー操作の失敗 | 無言で握り潰さない。理由をユーザーに返す |
| DB 例外 | per-user SAVEPOINT で局所化。全体ロールバックで他ユーザーを巻き込まない |

### 絶対にやってはいけないこと（本セクション固有）

1. **運用資産の変更（USDC → USDT 等）・チェーン移行を、実行パイプラインの課題解決策として
   提案・実装すること。** Base の Aave / Pendle に USDT 市場は存在しない
2. **縮退機能を通知経路より先に実装すること**（無断の設定変更になる）
3. **判定を出やすくする調整を、実行権限と到達経路の復旧より先に行うこと**
   （期限切れの母数が増えるだけで指標は悪化する）
4. **検知だけして通知しない実装**
5. **判定数・提案数を成果指標として扱うこと**
